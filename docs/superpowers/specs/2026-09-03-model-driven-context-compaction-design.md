# CodeN 模型驱动上下文压缩设计

## 1. 背景

CodeN 当前在上下文接近预算时，先由 `ContextManager` 将旧消息转换成确定性摘要：普通消息最多保留 500 个字符、工具结果最多保留 300 个字符，最终文本再截断到 6000 个字符。随后 `AgentRuntime` 将这份已经截断的文本交给当前模型润色。

该顺序会在模型参与前丢失文件路径、错误细节、用户约束、工具结果和中间决策。模型只能改写残缺摘要，无法从完整历史中判断哪些信息应被保留。模型请求失败时继续采用确定性摘要，还会把这种信息损失永久写入会话。

本设计将压缩改为模型直接读取待压缩历史并生成结构化交接摘要。确定性摘要及其失败兜底全部移除。

## 2. 目标

- 使用当前会话模型直接精炼完整待压缩历史。
- 在模型处理前不执行字符级摘要或有损确定性裁剪。
- 保留当前正在处理的交互，以及它之前最近一条完整交互。
- 保持工具调用与对应工具结果处于同一消息单元，不拆分。
- 通过“规划—生成—校验—提交”保证压缩状态原子更新。
- 压缩失败时保留原上下文，不用低质量摘要兜底。
- 自动、手动和紧急压缩使用同一核心流程，并提供符合各自场景的失败语义。
- 保持 session resume、双语提示、Provider 映射和 thinking level 隔离行为一致。

## 3. 非目标

本次不实现：

- 分块、多级或递归摘要；
- 第二次模型审校；
- 独立的 `compactionModel` 配置；
- OpenAI Responses API 原生 compaction；
- `/compact` 自定义聚焦指令；
- 确定性摘要或旧工具输出裁剪兜底；
- 修改 80% 自动触发阈值；
- 修改 `min(2048, reservedOutputTokens)` 摘要输出上限。

如果待压缩历史本身无法放入当前模型的一次请求，本次压缩失败；系统不为该极端情况引入分块机制。

## 4. 业界做法与取舍

### 4.1 Claude Code

Claude Code 的 `/compact` 与自动压缩会使用模型生成结构化摘要，并重新注入系统提示、项目级规则和部分持久内容。它还允许用户通过 `/compact` 参数指定关注点。其核心启示是：对话历史应由模型按语义提炼，而稳定规则应从持久来源重新注入。

### 4.2 OpenAI Codex

Codex 的本地 compact prompt 将压缩定义为“给另一个 LLM 的任务交接”，要求保留进度、决策、约束、剩余步骤和关键引用。OpenAI Responses API 另有 Provider 原生的加密 compaction item，但该能力不适合直接作为 CodeN 的跨 Provider 基线。

### 4.3 Gemini CLI

Gemini CLI 使用模型生成 `<state_snapshot>`，保留一部分近期历史，并对摘要进行第二次验证；它还拒绝空摘要和 token 数膨胀的结果。CodeN 采用其“生成后验证、失败不提交”的原则，但不采用二次模型调用和复杂工具输出预算，以保持实现极简。

### 4.4 采用方案

CodeN 使用单次模型调用生成结构化交接摘要，并在本地进行轻量有效性与预算校验。该方案比二次审校成本更低，比 Provider 原生压缩更一致，也避免分块摘要带来的额外状态机。

## 5. 消息单元与保留边界

`ContextManager` 按真实用户请求划分消息单元。一个单元从 `source !== "hook"` 的 user 消息开始，包含其后的 Hook 上下文消息、assistant 消息、assistant tool calls、对应 tool results 和最终 assistant 回复，直到下一个真实用户请求开始。`source: "hook"` 的 user 消息属于当前交互，不得单独开启消息单元。

每次规划压缩时：

1. 所有前导 system 消息永久保留，不进入摘要输入；
2. 当前正在处理、可能尚未完成的最后一个消息单元完整保留；
3. 最后一个单元之前最近的完整消息单元也完整保留；
4. 更早消息单元全部进入本次压缩输入；
5. 如果已有压缩摘要，该摘要与本次新增的旧消息单元一起交给模型，生成更新后的统一状态快照。

只有在确实存在可压缩的旧单元时才建立压缩计划。工具调用和结果不会跨计划边界拆开。

## 6. 架构

### 6.1 压缩计划

`ContextManager` 不再在 `prepare()` 或紧急路径中直接生成、安装摘要。它负责根据当前消息、已有摘要和触发模式构造压缩计划。计划至少包含：

- 交给模型的完整历史消息；
- 保留的近期消息单元；
- 候选压缩范围；
- 提交后用于主请求的投影基础；
- 触发类型：`automatic`、`manual` 或 `emergency`。

规划阶段是无副作用的。旧摘要、`compactedThrough` 和 `compactionRange` 在模型请求与校验成功前保持不变。

### 6.2 模型生成

`AgentRuntime` 执行压缩计划，使用当前会话的 Provider 和 `options.model` 发起一次请求。请求：

- 使用本地化压缩 system prompt；
- 携带计划中的完整历史消息；
- 不携带工具定义；
- 不设置主 Agent 的 `thinkingLevel`，保持 Provider 默认行为；
- 输出上限为 `min(2048, reservedOutputTokens)`；
- 复用当前操作的取消信号。

这不是对确定性摘要的“润色”，而是让模型直接从原始旧历史生成新的交接摘要。

### 6.3 摘要格式

模型返回普通 Markdown，而不是 JSON。提示词要求内容简洁、事实化，并按以下信息组织：

- 当前目标；
- 关键约束与用户偏好；
- 已完成工作与关键决策；
- 文件及代码状态；
- 工具、测试与验证结果；
- 未解决问题；
- 明确的下一步；
- 继续任务所需的关键数据、示例或引用。

提示词同时要求：

- 不推测未发生的工作或完成状态；
- 精确保留重要文件路径、命令、错误、关键数值和用户否决的方案；
- 检测到已有摘要时，合并其中仍然有效的信息并用较新事实更新它；
- 只输出摘要正文。

CodeN 在提交时于模型正文外添加本地化的“压缩后的对话摘要”标题。

### 6.4 校验与原子提交

模型结果必须同时满足：

1. 正文去除空白后非空；
2. 响应不包含 tool call；
3. 新摘要的估算 token 数严格小于被替换内容；
4. system 消息、新摘要和保留消息组成的完整主请求投影不超过硬输入预算。

任何条件失败都拒绝摘要。成功后，`ContextManager` 通过单一提交操作同时更新：

- 当前摘要；
- `compactedThrough`；
- `compactionRange`。

连续压缩时，范围的起点沿用已有范围的最早起点，终点更新为本次最后一个被压缩消息的索引。然后 Runtime 持久化新的 `context.compacted` 记录并发送成功事件。

## 7. 三类触发路径

### 7.1 自动压缩

当估算输入超过硬输入预算的 80%，且存在可压缩旧单元时，Runtime 执行压缩计划。

成功后使用新投影继续主模型请求。失败时：

- 发送 `context.compaction_failed`，记录错误类别与 `trigger: "automatic"`；
- 不修改上下文或 session compaction 记录；
- 如果原始投影仍处于硬输入预算内，继续当前主任务；
- 同一用户 turn 内不再重复自动压缩，下一 turn 可以再次尝试。

如果自动压缩失败且原始投影已经超过硬输入预算，则主请求不能安全继续，按 `context.exhausted` 处理。

### 7.2 手动 `/compact`

手动命令强制尝试建立压缩计划，不依赖 80% 阈值，但仍要求存在可压缩旧单元。它使用与自动压缩相同的模型生成、校验和提交逻辑。

成功时显示现有的“上下文已压缩”反馈。失败或没有足够历史可压缩时，命令返回明确结果，不得显示成功，也不得修改现有摘要。

### 7.3 紧急压缩

Provider 返回 413 或上下文长度类错误时，Runtime 最多执行一次紧急压缩并重试主请求。紧急压缩也保留当前交互与上一条完整交互，不采用更激进的“仅保留一个单元”策略。

若紧急压缩请求失败、摘要无效、压缩后仍超预算，或重试后 Provider 再次报告上下文超限，则抛出 `context.exhausted`。紧急路径不会静默删除旧消息。

## 8. 失败与取消语义

压缩失败包括：

- Provider 请求异常；
- 用户取消；
- 返回空正文；
- 返回 tool call；
- 摘要 token 数没有缩小；
- 新投影仍超过预算；
- 没有可压缩消息；
- 压缩请求本身超过模型上下文。

失败事件不再包含 `fallback: "deterministic"`。事件应包含触发类型和可诊断原因，但不得复制完整历史或敏感工具输入到 trace。

取消沿用当前操作的 `AbortSignal`。取消不会提交摘要，也不会写 session compaction 记录。主 turn 的既有取消语义保持不变。

## 9. Session 与恢复

消息历史仍完整追加到 JSONL session；压缩只改变后续发送给模型的投影，不删除历史记录。

每次成功压缩追加一条 `context.compacted`，包含摘要和压缩范围。失败不追加记录。恢复会话时继续采用最后一条成功记录，并从其范围之后识别未压缩消息。

`/new` 继续清除当前摘要和范围。语言切换不重写已有摘要；后续压缩可用当前语言生成新的统一摘要。

## 10. 测试策略

### 10.1 ContextManager 单元测试

覆盖：

- 自动阈值判断与无副作用压缩计划；
- 当前交互和上一条完整交互保持原文；
- 更早单元完整进入模型输入，不发生 300/500/6000 字符截断；
- 多工具调用与结果不拆分；
- 已有摘要进入下一次计划；
- 成功提交同时更新摘要、范围和投影；
- 拒绝提交时状态完全不变；
- 连续压缩范围正确延续。

### 10.2 Runtime 集成测试

使用 `ScriptedProvider` 覆盖：

- 自动、手动和紧急路径都调用当前模型；
- 压缩请求无工具且不设置 thinking level；
- 完整旧历史实际发送给模型；
- 成功摘要被用于随后的主请求并持久化；
- 空摘要、tool call、膨胀摘要、超预算摘要和 Provider 异常均不提交；
- 自动失败后同一 turn 不重复尝试，下一 turn 可重试；
- 自动失败但仍在硬预算内时主任务继续；
- 手动失败向调用方报告失败；
- 紧急失败抛出 `context.exhausted`；
- 紧急成功后只重试主请求一次；
- 取消不会留下压缩记录。

### 10.3 回归测试

确保以下行为保持通过：

- session resume 使用最新有效摘要；
- OpenAI 与 Anthropic 历史消息映射；
- Anthropic thinking/provider state 的既有持久化与淘汰边界；
- 主 turn thinking level 不泄漏到压缩请求；
- `/compact`、`/new`、CLI 和 TUI 命令反馈；
- 中英文 i18n key 完整性；
- 工具调用与结果配对安全。

## 12. 验收标准

1. 压缩模型能够看到全部待压缩原始消息，不接收确定性摘要。
2. 代码中不再存在用于上下文压缩的 300/500/6000 字符摘要逻辑。
3. 当前交互和上一条完整交互始终原样保留。
4. 摘要失败或无效时，上下文、范围和 session 不发生部分更新。
5. 自动压缩失败不会在同一 turn 重复调用模型；后续 turn 可以重试。
6. 手动压缩只在成功后报告成功。
7. 紧急压缩失败明确产生 `context.exhausted`，不使用确定性兜底。
8. 连续压缩与 session resume 保持正确。
9. 中英文文档与实现一致。
10. `just check`、`just website-check`、`just build` 和 `git diff --check` 全部通过。
