# CodeN 系统提示词优化与中英文 i18n 设计

## 1. 背景

CodeN 当前的主系统提示词只有一句通用约束，不能充分指导模型遵循项目指令、选择工具、汇报进度、验证修改和交付结果。CLI、REPL、权限确认、终端状态、配置错误、内建工具描述及工具结果又以散落的英文字符串为主，中文用户无法获得一致体验，也无法在运行期间切换语言。

本设计同时解决两个相关问题：

1. 参考 Codex CLI 的成熟行为契约，按 CodeN 的真实能力重写系统提示词；
2. 建立轻量、类型安全、零运行时依赖的中英文 i18n 基础，使系统提示词、工具提示词、应用内讯息和 README 使用统一的语言策略。

两项工作共享同一语言状态，但保持组件边界清晰：运行时语言包负责 CodeN 应用和模型上下文，README 使用独立双文件维护。

## 2. 目标

首版实现以下目标：

1. 仅支持中文和英文，规范语言代码为 `zh` 与 `en`；
2. 缺省语言固定为中文，不根据操作系统区域自动变化；
3. 允许用户通过用户级 `config.json`、启动参数 `--lang` 和 REPL `/lang` 选择语言；
4. `/lang` 列出支持语言，`/lang en` 或 `/lang zh` 持久化用户偏好并立即切换当前进程；
5. 统一本地化 CodeN 自有的用户可见文案和模型可见文案；
6. 使用完整但精炼、与 CodeN 能力一致的中英文系统提示词；
7. 语言热切换后，应用讯息立即生效，下一次模型请求使用新语言的系统提示词与内建工具描述；
8. 保持第三方插件 API 和插件作者提供的工具描述不变；
9. 提供内容等价的中文 `README.md` 和英文 `README.en.md`，顶部互相链接；
10. 不引入 Bun 专有 API，构建产物继续只依赖 Node.js 运行时。

## 3. 非目标

首版不实现：

- 中文、英文之外的语言；
- 根据系统区域、用户输入文本或模型自动检测界面语言；
- 分离“界面语言”和“Agent 默认回复语言”；
- 项目级语言覆盖；
- `CODEN_LANG` 环境变量；
- 第三方插件描述的自动翻译或多语言插件 API；
- 运行时机器翻译；
- ICU MessageFormat、复杂复数规则或日期区域格式化框架；
- 自动同步两份 README 的翻译服务；
- 对历史会话消息或已有 compact 摘要进行翻译；
- 复制 Codex CLI 中 CodeN 不具备的 `update_plan`、`apply_patch`、MCP、沙箱参数或审批协议。

## 4. 方案选择

### 4.1 采用：类型安全的 TypeScript 语言包

新增 `src/i18n/` 模块，以中文语言包作为消息键和函数签名的类型基准，英文语言包必须完整满足相同类型。运行时通过一个轻量 `I18n` 实例读取当前语言、执行插值并切换语言。

优点：

- 编译期发现缺失键、参数签名不一致和返回类型错误；
- 不增加依赖；
- 不需要处理构建后 JSON 文件路径或资源复制；
- 文案可以使用普通 TypeScript 函数处理动态参数；
- 适合只有两种语言、单个 CLI 进程的当前规模。

### 4.2 不采用：JSON 资源包和通用加载器

JSON 便于非开发者编辑，但需要额外解决运行时资源定位、打包、键类型生成、插值、缺失回退和错误处理。对于首版两种语言，这些复杂度没有足够收益。

### 4.3 不采用：各模块直接判断语言

在每个调用点使用 `language === "zh" ? ... : ...` 改动较小，但文案会继续散落，难以审计漏译，也无法保证系统提示词和工具描述语义一致。

## 5. 语言模型与优先级

定义：

```ts
export const SUPPORTED_LANGUAGES = ["zh", "en"] as const;
export type Language = (typeof SUPPORTED_LANGUAGES)[number];
export const DEFAULT_LANGUAGE: Language = "zh";
```

启动时的有效语言优先级固定为：

```text
--lang <zh|en>
  > 用户级 ~/.config/coden/config.json 的 language
  > 中文 zh
```

具体规则：

- `--lang` 只覆盖当前进程，不写配置；
- `/lang <zh|en>` 写入用户配置并切换当前进程；
- 项目 `.coden/config.json` 中的 `language` 不参与解析，不能改变个人界面或 Agent 语言；
- 不读取 `LANG`、`LC_ALL` 或其他系统区域变量；
- 配置中只接受规范值 `zh` 与 `en`，不接受 `zh-CN`、`cn`、`english` 等别名；
- 对用户明确要求使用其他语言的单次任务，Agent 可以遵从用户，但这不会改变 CodeN 的界面语言或持久化偏好。

## 6. i18n 模块架构

建议结构：

```text
src/i18n/
├── index.ts            # 公共类型、SUPPORTED_LANGUAGES、DEFAULT_LANGUAGE
├── i18n.ts             # I18n 实例、读取和切换
├── config.ts           # 启动语言解析、用户偏好原子写入
└── locales/
    ├── zh.ts           # 中文基准语言包
    └── en.ts           # 英文等价语言包
```

语言包可以包含字符串和带参数的函数：

```ts
export const zh = {
  cli: {
    description: "CodeN — 极简编程智能体",
  },
  repl: {
    languageChanged: (name: string) => `语言已切换为 ${name}。`,
  },
} as const;

export type Messages = WidenMessages<typeof zh>;
export const en: Messages = {
  cli: {
    description: "CodeN — a minimal coding agent",
  },
  repl: {
    languageChanged: (name) => `Language changed to ${name}.`,
  },
};
```

实现可以使用等价的类型映射，但必须保证英文包在编译期具备与中文包相同的键和函数参数。

### 6.1 `I18n` 职责

`I18n` 是进程内共享的可变语言上下文，职责限定为：

1. 持有当前 `Language`；
2. 返回当前语言包中的消息；
3. 原子更新当前语言；
4. 提供支持语言的稳定列表和显示名；
5. 不负责文件 I/O、Commander 参数解析或模型调用。

调用方可以持有同一个 `I18n` 引用，因此 `/lang` 成功后无需重新构造终端渲染器。语言状态更新是同步操作，不暴露中间状态。

### 6.2 缺失键策略

语言包完整性由 TypeScript 类型检查保证，不在生产环境静默回退到另一语言。若开发期间通过不安全转换制造缺失键，测试必须失败；运行时不向用户显示原始消息键。

## 7. 启动前语言引导

Commander 的帮助文本在创建命令树时确定，而完整 `loadConfig()` 当前在命令 action 内异步执行。为保证 `coden --help` 和插件子命令帮助从启动开始即采用目标语言，需要在创建完整 CLI 前完成轻量语言引导。

流程如下：

1. 从原始 `process.argv` 中只预解析 `--lang <value>` 和 `--lang=<value>`；
2. 读取用户级 `~/.config/coden/config.json` 的顶层 `language`；
3. 按优先级解析有效语言，默认中文；
4. 创建共享 `I18n`；
5. 使用该实例创建 Commander 主命令和插件子命令；
6. Commander 再执行完整参数解析和现有 action。

预解析器只识别语言参数，不替代 Commander，不改变其他参数的顺序、错误或 `--` 语义。`--lang` 仍作为正式 Commander option 注册，以便出现在帮助中并传入 Agent 配置。

公开的 `createCliProgram` 应接受可选语言或 `I18n` 依赖，使测试和嵌入调用不依赖真实用户配置。可执行入口负责调用异步 bootstrap；测试未传入时使用中文。

### 7.1 启动错误语言

- 用户配置 `language` 无效时，在 CLI 尚无可信语言的情况下使用中文兜底错误，明确列出 `zh`、`en`；
- `--lang` 的值有效时，即使用户配置语言无效，也以命令行覆盖值启动；
- `--lang` 无效时，若用户配置语言有效则用用户配置语言显示参数错误，否则用中文；
- 用户配置文件的底层 JSON 解析错误保留原始异常摘要，并包裹在本地化上下文中。

## 8. 配置读取与持久化

### 8.1 用户级专属字段

`language` 是用户偏好，不遵循普通配置的“用户 → 项目 → 环境 → CLI”合并链。实现必须显式区分配置来源：

- 只从用户级 `config.json` 读取持久化语言；
- 项目配置中的同名字段被忽略；
- `CodeNConfig.language` 保存本次进程最终有效值，供运行时组合使用；
- CLI override 可以传入完整配置加载，但不能被写回磁盘。

项目配置中出现 `language` 不报错，以便配置文件可跨版本使用，但它没有效果。README 必须明确这一点。

### 8.2 `/lang` 原子写入

新增用户语言偏好写入函数，执行：

1. 读取现有用户 `config.json`；文件不存在时以空对象开始；
2. 要求根值为普通 JSON 对象；
3. 只更新顶层 `language`，保留所有其他已知和未知字段；
4. 确保配置目录存在；
5. 在同目录创建临时文件，以 UTF-8 写入格式化 JSON 和末尾换行；
6. 临时文件使用 `0600` 权限，替换后的用户配置也保持 `0600`；
7. 通过 rename 原子替换目标文件；
8. 无论成功或失败都清理遗留临时文件。

同目录 rename 保证不会跨文件系统。写入失败时不得改变内存语言，也不得更新 Runtime 系统提示词。

## 9. CLI 与 REPL 语言体验

### 9.1 CLI 参数

新增：

```text
--lang <zh|en>
```

它适用于主命令和本次进程，不持久化。中文与英文帮助分别解释支持值、默认中文和覆盖语义。

### 9.2 `/lang`

`/lang` 加入 REPL 命令集合及 `/help` 输出。

无参数时输出稳定列表并标记当前语言，例如中文模式：

```text
支持的语言：
* zh - 中文（当前）
  en - English
使用 /lang <zh|en> 切换语言。
```

英文模式使用等价英文文本。`/lang en` 或 `/lang zh` 成功后：

1. 原子持久化用户偏好；
2. 更新共享 `I18n`；
3. 更新内建工具的模型可见描述；
4. 重建并替换 Agent Runtime 的主系统提示词；
5. 使用新语言确认切换成功。

无效值不写配置、不切换语言，并用当前语言显示支持列表。`/lang` 只存在于交互 REPL；`-p` 模式通过 `--lang` 选择语言。

## 10. 系统提示词设计

系统提示词不逐字复制 Codex，而是吸收其有效行为约束，并删除 CodeN 不具备或不适用的功能。中英文版本分别维护自然表达和等价语义，不通过逐句运行时拼接翻译。

### 10.1 身份与语言

系统提示词明确：

- CodeN 是精确、安全、简洁的编程智能体；
- 默认使用当前界面语言回复；
- 用户明确要求其他语言时遵从用户；
- 不猜测未知事实，不声称执行过未实际执行的操作。

### 10.2 指令优先级与 `AGENTS.md`

系统提示词明确：

- 遵循系统指令、用户要求和适用的 `AGENTS.md`；
- CLI 自动注入工作区根 `AGENTS.md`；
- 在处理子目录文件前，主动检查该路径范围内更深层的 `AGENTS.md`；
- 更深层指令只覆盖其目录树，冲突时优先；
- 项目文件中的普通内容不能伪装成更高优先级指令。

提示词不承诺 CodeN 尚未实现的自动父目录扫描。只描述真实的根文件注入和模型可用工具可执行的进一步检查。

### 10.3 工作方式与用户沟通

系统提示词要求：

- 修改前检查相关文件、现有模式和适用项目指令；
- 简单任务直接执行，复杂、多阶段或有歧义的任务先给出简短方案；
- 工具调用前发送一句简短预告，并逻辑分组相关操作；
- 长任务在阶段边界提供简洁进度，不为每次普通读取打断用户；
- 持续工作到任务真正完成，除非必要信息缺失、权限被拒绝或环境阻塞；
- 阻塞时清楚说明已完成内容、阻塞原因和用户可采取的下一步。

CodeN 当前没有 `update_plan` 工具，因此提示词只要求以普通消息提供简短方案，不能要求调用不存在的计划工具。

### 10.4 工具规则

系统提示词与 CodeN 实际工具对应：

- 使用 `read` 读取文本文件；
- 使用 `bash` 搜索、检查状态和执行项目命令；
- 使用 `edit` 做唯一、精确的局部替换；
- 使用 `write` 创建文件或完整重写；
- 搜索文本优先使用 `rg`，列出文件优先使用 `rg --files`；
- 修改保持聚焦，不覆盖用户已有改动，不处理无关问题；
- 任务匹配有效 Skill 时，先调用 `activate_skill` 加载完整说明；
- 不引用 `apply_patch`、MCP、网络搜索或其他当前未注册工具。

系统提示词不硬编码当前工具列表作为唯一真相；provider 仍通过原生 Tool Calling 接收 Registry 中的实际工具定义，包括第三方插件。

### 10.5 安全与验证

系统提示词要求：

- 对危险、不可逆或影响范围不清晰的操作保持谨慎；
- 不主动执行无关删除、重置、提交、发布或修改系统状态；
- 遵守 CodeN 的权限确认结果，不尝试绕过拒绝；
- 优先修复根因，避免为通过测试制造表面补丁；
- 从与修改最相关的测试开始，再按需要运行类型检查、lint、构建和更广测试；
- 不修复与任务无关的失败，但在最终答复中明确指出；
- 未实际验证的内容必须标记为未验证。

提示词只描述行为，不把权限机制误称为安全沙箱。

### 10.6 最终答复

系统提示词要求最终答复：

- 像简洁协作者交接工作；
- 优先说明完成内容、验证结果、残余风险和必要后续步骤；
- 简单任务用短段落，复杂结果才用短标题和列表；
- 文件路径、命令、配置键和代码标识使用反引号；
- 不重复粘贴已经写入的大段文件内容；
- 不输出 CodeN UI 不支持的特殊文件引用语法。

### 10.7 动态区块

系统提示词由稳定语言模板和动态区块组成：

```text
核心行为契约

当前语言规则

项目指令（存在时）

可用 Skill 目录（存在时）
```

项目指令原文不翻译。Skill 名称和描述由 Skill 作者决定，目录标题和激活说明本地化。

## 11. 系统提示词热切换与会话语义

`AgentRuntime` 新增明确的系统提示词更新能力，例如：

```ts
updateSystemPrompt(content: string): void;
```

更新规则：

1. 只替换 `messages` 中首条主系统消息；
2. 不修改用户、助手、工具消息；
3. 不修改已有 compact 摘要；
4. 下一次 `context.prepare()` 使用新的主系统消息；
5. `/new` 保留当前语言的新系统消息；
6. 恢复会话时，仍按当前有效语言重新构建并替换恢复记录中的首条系统消息。

当前 session 日志中较早写入的系统消息可以保留作为历史记录；恢复路径本来就会用当前构建结果替换首条系统消息，因此无需重写 append-only 日志。语言切换可以记录不含敏感内容的 session/event 元数据，但不是恢复正确性的依赖。

## 12. 内建工具本地化

当前内建工具是模块级单例。为支持共享语言状态，改为工厂或等价的动态定义：

```ts
builtinTools(skills, i18n): ToolDefinition[]
```

本地化范围包括：

- 工具 `description`；
- JSON Schema 属性 `description`，若实现中提供；
- CodeN 自己生成的成功、失败、截断和状态文本；
- `activate_skill` 的固定包装文本。

保持不变：

- 工具名：`read`、`write`、`edit`、`bash`、`activate_skill`；
- Schema 属性名和机器结构；
- 风险枚举；
- 稳定错误码，如 `edit.no_match`、`bash.spawn_error`；
- metadata 字段；
- Bash 子进程的原始 stdout、stderr 和系统错误文本。

工具对象可以通过 getter、语言代理或 Registry 中的内建定义刷新实现热切换，但必须满足：

1. 当前执行中的工具调用不因语言切换改变语义；
2. 下一次 provider 请求获得新语言描述；
3. 第三方插件对象、描述和 Registry 来源不被重写；
4. 插件 reload 后仍保留当前语言的内建工具；
5. 工具 Schema 的验证行为不变。

## 13. 应用内讯息本地化边界

首版本地化所有 CodeN 自有、用户可见或模型可见的固定文本，包括：

- 主 CLI 与插件子命令的 description、argument、option 和确认问题；
- 参数解析器生成的 CodeN 自定义错误；
- 配置读取和校验错误的固定上下文；
- REPL banner 周边文本、帮助、会话、新对话、compact、reload、语言列表和切换结果；
- 会话列表、恢复摘要标题、工具调用汇总和省略提示；
- 权限问题、选择说明和工作区信任提示；
- TerminalRenderer 的 thinking、review、tool、provider、plugin 和 turn 状态；
- Skill 目录和列表的固定文本；
- npm 插件管理的 CodeN 固定输出；
- 主 Agent、compact 摘要器和智能审批器提示词；
- 内建工具描述和固定结果文本。

以下机器标识或外部内容保持原样：

- 命令名、参数名、配置键、环境变量名；
- 工具名、事件名、错误码、风险值、JSON 字段和协议值；
- `stdout`、`stderr`、exit code、signal 等标准技术标识；
- 文件路径、包名、模型 ID、session ID；
- 第三方插件名称、描述、结果和错误；
- 操作系统、Node.js、provider 和底层库产生的原始错误摘要；
- 用户输入、项目 `AGENTS.md` 和 Skill 作者文本。

外部原文可以嵌入本地化固定上下文，例如“插件加载失败：<原始错误>”，但不运行时翻译或改写。

## 14. 智能审批器与 compact 提示词

### 14.1 智能审批器

`LlmApprovalReviewer` 使用当前语言构建独立系统提示词：

- 安全规则和 strictness 语义在中英文版本中等价；
- 仍要求只输出包含 `decision` 与 `reason` 的单个 JSON 对象；
- `decision` 机器值保持 `allow | human_review`；
- 要求 `reason` 使用当前语言；
- payload 字段和不可信数据边界保持稳定英文机器标识；
- 语言切换后下一次审批请求使用新语言，不影响正在进行的审批请求。

审批结果解析、安全边界和 fail-closed 语义不因 i18n 改变。

### 14.2 compact 摘要器

自动 compact 的润色提示词跟随当前语言，并要求摘要使用当前语言。确定性摘要的固定标题和字段标签也本地化。语言切换不会重写已有摘要；后续再次 compact 时可以生成新语言摘要，因此同一会话中允许存在不同语言的历史摘要内容。

## 15. 热切换数据流

`/lang en` 的完整成功路径为：

```text
解析并校验 en
  → 读取用户 config.json
  → 原子写入 language: "en"
  → i18n.setLanguage("en")
  → 重新构建主系统提示词
  → runtime.updateSystemPrompt(...)
  → 使用英文输出成功讯息
  → 下一次模型请求读取英文工具描述和系统提示词
```

失败语义：

- 参数无效：不写配置，不切换；
- 配置读取、序列化、权限、临时文件或 rename 失败：不切换；
- 系统提示词重建使用纯函数，正常情况下不会失败；若意外失败，应恢复旧内存语言并报告错误；
- 切换命令串行处理，不与新的用户 turn 并发执行；
- 已经开始的模型请求、审批请求或工具调用不在中途改变语言。

## 16. README 双语策略

文档采用两个完整文件：

- `README.md`：中文，作为仓库和 npm 的缺省 README；
- `README.en.md`：内容等价的英文版本。

两个文件标题下方提供互链：

```text
[中文](README.md) | [English](README.en.md)
```

README 必须同步说明：

- CodeN 默认中文；
- `--lang zh|en` 只覆盖当前进程；
- 用户级 `config.json` 的 `language`；
- 项目配置不能覆盖语言；
- `/lang` 列表和 `/lang <language>` 持久化、立即切换语义；
- 系统提示词、内建工具和界面使用同一语言；
- 用户明确要求其他回复语言时 Agent 可以遵从；
- 第三方插件文本保持插件作者原文。

代码示例、命令、配置键和协议值在两份 README 中保持一致。实现本功能时应顺便修正 README 中与当前版本或实际 CLI 行为不一致的直接相关内容，但不重写无关章节。

## 17. 错误处理

### 17.1 配置错误

- `language` 非字符串或不是 `zh | en` 时属于配置错误；
- 错误必须明确指出配置来源和支持值；
- 用户配置根值不是对象时，`/lang` 不得覆盖原文件；
- 项目配置中的 `language` 被忽略，不触发值校验；
- `--lang` 无效时由本地化参数解析错误处理。

### 17.2 文案插值

所有外部字符串在终端显示前继续经过现有净化与宽度截断路径。i18n 函数只负责语言和句式，不承担终端安全。不得把未经净化的模型 reason、插件错误或路径直接拼进可控制终端的特殊序列。

### 17.3 机器协议

本地化不得改变 provider tool schema 的结构、审批 JSON 协议、事件 payload、session 文件 Schema、退出码和错误码。测试应优先断言稳定机器值，而不是依赖整段自然语言。

## 20. 验收标准

实现满足以下条件即验收：

1. 未配置语言时，CodeN CLI、REPL、系统提示词和内建工具默认使用中文；
2. `--lang en` 在启动帮助和本次运行中完整切换英文，但不写用户配置；
3. 只有用户级 `config.json` 的 `language` 生效，项目配置不能覆盖；
4. `/lang` 显示 `zh`、`en` 和当前语言；
5. `/lang <language>` 原子持久化并立即切换应用讯息；
6. 下一次模型请求使用新语言的主系统提示词、Skill 固定说明和内建工具描述；
7. 系统提示词覆盖身份、语言、指令优先级、`AGENTS.md`、工作方式、真实工具、安全、验证和最终答复，并且不引用不存在的能力；
8. 用户明确要求其他回复语言时，Agent 可以遵从而不改变持久化语言；
9. 所有 CodeN 自有用户可见固定文本纳入语言包或明确的语言化构造器；
10. 命令名、配置键、工具名、错误码、事件和 JSON 协议保持稳定；
11. 第三方插件描述和输出保持作者原文，插件 API 不变；
12. 历史消息与 compact 摘要不因热切换被篡改，resume 使用当前语言重建主系统消息；
13. `README.md` 与 `README.en.md` 内容等价并互相链接；
14. 全部聚焦测试、`just check`、构建和双语帮助冒烟测试通过；
15. 构建后的 CLI 继续在 Node.js 下运行，不依赖 Bun 专有 API。
