# CodeN 入门文档首批撰写设计

## 背景

`website/src/content/docs/` 已建立中英文文档信息架构，但当前 100 个页面仍是仅含 frontmatter 和占位提示的骨架。本轮启动正式文档撰写，并按栏目分批交付。

首批聚焦文档入口和入门指南。目标读者是熟悉终端、软件工程和主流编程智能体的技术专家。文档以最短任务路径帮助其完成安装、Provider 配置和首个任务，并精确说明可验证的行为、边界和失败模式。

## 目标

- 完成文档入口及入门指南的 6 组中英文页面。
- 所有技术事实严格对应当前代码、测试和实际命令行为。
- 先完成并核验中文，再以相同事实和结构撰写自然英文。
- 建立后续栏目可复用的高密度页面结构、核验流程和双语术语约束。
- 保持现有 URL、侧栏顺序和站点信息架构稳定。

## 非目标

- 本批次不撰写概念、配置、界面、插件、Skills、Hooks、高级或参考栏目正文。
- 不描述尚未实现或只存在于路线图中的能力。
- 不借入门页面完整复述配置参考或安全模型。
- 不调整网站视觉设计、导航架构或文档路由。
- 不为无法从当前仓库稳定验证的平台或环境作保证。

## 用户旅程

六个主题组成一条连续的首次使用路径：

1. 文档入口说明 CodeN 的用途，并给出最短上手路径。
2. 环境要求帮助用户确认运行前提。
3. 安装页完成安装、版本确认和升级说明。
4. Provider 页完成 OpenAI 或 Anthropic 的最小可用配置，并链接详细配置文档。
5. 第一个任务页从进入工作区开始，展示一次可验证的基础任务流程。
6. 界面选择页解释 CLI、Print 和 TUI 的适用场景，并引导至各自的详细页面。

每页只承担一个主要用户任务。跨栏目细节通过链接渐进披露，避免入门指南与参考手册重复。

## 页面内容模型

页面根据主题裁剪，但原则上依次包含：

1. **目标与前置条件**：用最少文字说明任务和必要环境，不解释技术通识。
2. **最短可用步骤**：直接提供准确、可复制的命令和最小配置。
3. **行为说明**：精确记录默认值、配置来源、状态变化和副作用。
4. **验证**：提供可执行检查及预期输出特征。
5. **边界与失败模式**：说明安全边界、优先级、平台限制和典型错误。
6. **相关参考**：链接到配置、CLI、安全模型或用户旅程中的后续页面。

这不是要求所有页面机械地使用六个同名标题。文档入口和界面选择页可以采用更适合其任务的标题，但仍应覆盖对应信息。

## 写作风格

- 以用户要完成的任务组织内容，不按源码模块罗列。
- 假设读者熟悉 shell、环境变量、JSON、Provider API Key、工作目录、软件包管理和编程智能体，不解释这些基础概念。
- 优先使用表格、命令块和明确规则，减少叙述性过渡，保持高信息密度。
- 标题、步骤和提示框保持简洁，支持快速扫描和定位。
- 默认值、覆盖顺序、状态变化和副作用必须有源码依据；无法核实则省略。
- 中文使用自然、克制、直接的技术语言；避免宣传口号、不必要的拟人化表达以及与同类工具的营销式对比。
- 英文与中文保持相同事实、顺序和意图，但按英文技术文档习惯重写，不逐字翻译。
- 产品名、命令、选项、环境变量、配置键和界面名称保持源码中的原始拼写。
- 删除所有 `Documentation scaffold` 占位提示。

## 事实核验

技术陈述按以下优先级核实：

1. 当前源码中的实际行为；
2. 自动化测试覆盖的行为；
3. 构建产物的帮助信息和实际命令输出；
4. `package.json`、配置 schema 和仓库内示例；
5. README 等现有说明。

若低优先级说明与源码或测试冲突，以可执行实现为准。实施阶段为每页维护内部事实来源清单，用于复核命令、默认值和行为；该清单不直接堆入面向用户的正文。

重点核验：

- 支持的运行时与版本要求；
- 安装、升级和版本检查命令；
- Provider 名称、认证方式和最小配置；
- CLI 入口、界面模式及相关选项；
- 工作区、信任和审批在首次任务中的可见行为；
- 配置优先级、默认值及环境变量；
- 页面间实际存在的中英文链接。

无法稳定验证的行为不作推测。若不是完成入门流程的必要信息，应省略；若确有必要，应将表述限定在已验证范围内。

## 示例与安全

- 命令应在构建产物或仓库脚本中实际执行后再写入正文。
- API Key 和其他秘密只使用明显占位符，不使用真实凭据。
- 冒烟测试优先在临时目录中运行，避免修改用户全局配置。
- 需要展示配置时，明确文件作用域和写入位置，不暗示未验证的默认路径。
- 对可能访问工作区外部、执行命令或产生费用的步骤使用恰当警告。
- 平台差异仅记录仓库明确支持或实施阶段能够验证的内容。

## 双语工作流

本批次采用栏目批次法：

1. 审计六个主题对应的源码、测试和现有说明。
2. 建立本批次术语与事实清单。
3. 完成六个中文页面。
4. 对中文页面执行技术核验和用户旅程检查。
5. 按已核验结构完成六个英文页面。
6. 比较中英文标题层级、命令、链接、警告和技术事实。
7. 运行站点及仓库验证。

后续栏目继续使用相同流程，但每个栏目独立规划和交付，不在本批次一次性展开全部 100 个页面。

## 验收标准

- 12 个目标页面均包含完整正文，不含 scaffold、TODO、TBD 或其他占位内容。
- 中英文对应页面的章节意图、命令、链接、警告和技术事实一致。
- 示例命令与当前构建产物或仓库脚本一致，并完成冒烟验证。
- 所有内部链接在配置的 base path 和双语路由下有效。
- MDX 内容可被 Astro 和 Starlight 正常解析。
- Pagefind 可为两种语言建立索引。
- 现有 built-site validator 通过。
- `just website-check` 和 `git diff --check` 通过。
- 若实施改动触及网站内容以外的共享行为，则额外运行 `just check`。
- 当前工作区已有的 `website/tsconfig.json` 修改不被覆盖或纳入本批次提交。

## 交付方式

设计规格独立提交。设计获用户确认后，再编写实施计划。正式实现作为一个首批入门文档提交交付，提交只包含本批次文档及为验证这些文档所必需的紧密相关改动。
