## Execution model

- All hooks matching the same event run **in parallel** (`Promise.all`), with results merged in config order.
- Each hook is an independent system-shell child process (process group) with the workspace as its cwd.
- The event payload arrives as JSON on stdin (1MB limit).

## Timeouts

| Parameter | Default | Range |
| --- | --- | --- |
| `timeout` (config) | 10 seconds | 1–600 seconds (integer) |

- On timeout, `SIGTERM` goes to the process group; if it has not exited after 500ms, `SIGKILL` (Windows terminates the process directly).
- Timeout result: `timedOut: true`, counted as a hook failure (never blocks).
- On user cancellation (`Ctrl+C`) hooks cancel: `cancelled: true`, rethrown with the main-task abort.

## Limits

| Channel | Cap | Over-limit behavior |
| --- | --- | --- |
| stdin | 1MB | `inputExceeded`, counted as a failure |
| stdout | 10KB | process terminated immediately, `outputExceeded` |
| stderr | 10KB | same |

## Failure semantics

| Result | Handling |
| --- | --- |
| exit `0`, empty stdout | no-op (`hook.completed`) |
| exit `0`, valid JSON | processed per protocol (decision/context/system message) |
| exit `2` (controllable events) | explicit block |
| non-zero, timeout, over limit, invalid JSON, illegal fields | `hook.failed`: diagnostic stderr (≤2000 chars, scrubbed) and fail open |

Fail-open means: decision hooks that fail produce **no decision**, and permissions continue through the policy layer; unsafe scenarios are decided by that layer (a failed `PermissionRequest` never silently allows).

## Visibility

- Successful hooks show under `--verbose`; failures, blocks, and input conflicts always show.
- Hook runtime events (`hook.started`/`completed`/`failed`/`blocked`) are written to the trace.
- `systemMessage` output goes to the diagnostic sink (stderr).
