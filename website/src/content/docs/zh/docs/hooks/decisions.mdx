## 决策入口

| 事件 | 决策字段 | 效果 |
| --- | --- | --- |
| `PreToolUse` | `hookSpecificOutput.permissionDecision`：`allow`/`ask`/`deny` | 预判权限：`deny` 直接拒绝（`permission.hook_denied`）；`ask` 强制人工；`allow` 跳过策略层 |
| `PermissionRequest` | `hookSpecificOutput.decision.behavior`：`allow`/`ask`/`deny`（可带 `message`） | 在策略层要求人工时触发，可覆盖最终决定 |
| `Stop` | 顶层 `decision: "block"` + `reason` | 注入反馈要求模型继续 |
| 可控事件 + 退出码 `2` | stderr 作为 `blockReason` | 等同于 `deny`/阻止 |

## PreToolUse 的完整顺序

1. `PreToolUse` Hook 决策（含 `updatedInput` 与 `additionalContext`）。
2. 输入更新后**重新校验**：schema（失败为 `hook.invalid_updated_input`）、结构化文件路径、风险分类、权限。
3. 策略层（`manual`/`smart`/`auto`）。
4. 需要人工时触发 `PermissionRequest` Hook（`reason: "policy"`；若 Hook 请求人工则为 `"hook"`）。
5. 人工确认（CLI/TUI 内联）。
6. 执行工具并触发 `PostToolUse`/`PostToolUseFailure`。

## 合并语义

同一事件的多个 Hook **并行执行**，结果按配置 `order` 排序：

- 权限决策按 `deny > ask > allow` 合并（非 `deny` 的决策可能与 `allow` 覆盖，取最保守）。
- 多个 `updatedInput` 冲突时**全部作废**（`inputConflict`），不应用任何更新。
- 任一 `blocked` 即整体阻止。
- 每个 `additionalContext` 注入为独立的 `[CodeN hook context: <event>]` 消息；总上限 10KB。

## 与审批模式的交互

| 模式 | Hook 行为 |
| --- | --- |
| `manual` | `PreToolUse` 决定生效；策略层人工确认；`PermissionRequest` 可覆盖 |
| `smart` | 同上；普通修改先由 LLM 审查，Hook 的 `deny` 优先于 LLM 放行 |
| `auto` | 仍执行 `PreToolUse`：`deny` 生效；`ask` 安全拒绝（`permission.hook_requires_interaction`） |
